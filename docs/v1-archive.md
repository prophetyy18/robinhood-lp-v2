## 二、值得带走的：协议层的东西

这些是**协议事实和产品知识**，不是流程产物。换流程不该丢掉。

### 2.1 双 provider 的能力差异（ADR-010，2026-09-16 实测）

这不是文档，是实测结论。免费方案的 A+B 组合各有硬限制：

| | 官方公开 RPC | Alchemy Free |
|---|---|---|
| chain_id | 4663 ✓ | 4663 ✓ |
| 区块头/receipt/block-pinned call | ✓ | ✓ |
| `eth_getLogs` 区块跨度 | 100,000 块 ✓ | **最多 10 块** |
| 100 万块前的历史状态 | **不可用** | ✓ |

**这个差异直接决定入库策略**：官方端点做低频宽范围扫描，Alchemy 做高密度
窄范围回填。任何忽略这条的采集设计都会在第一次跑历史数据时卡死。

另外：urllib 默认 User-Agent 被官方端点返回 **HTTP 403**，httpx 可以正常读。
所以传输层的 header 必须显式设置，这个也是实测才发现的。

### 2.3 V4 的结构性事实

- V4 的池**不是独立合约**，是 `PoolManager` 里的 `PoolId = keccak256(abi.encode(PoolKey))`
- 因此**不存在"池地址"这种输入**。任何 20 字节地址都必须明确拒绝，不能猜测或兜底
- `PoolId` 不可逆，要解出 `PoolKey` 必须扫 `Initialize` 事件
- 一个 token 可以对应多个 `PoolKey`（不同配对 token / fee / tickSpacing / hooks），
  它们不是同一个池，风险也不同

最后一条是产品约束而非技术事实：目标 token 由用户人工输入并审批，
系统不得按收益、热度、舆情自动选择或切换。

### 2.4 整数/小数双域策略（ADR-004）

链上值（`sqrtPriceX96`、liquidity、tick、amount、feeGrowth）一律用 Python `int`
或项目类型包装（`Uint256`/`Tick`/`SqrtPriceX96`/`Liquidity`）。
只在**展示和统计分析的明确边界**转 Decimal。

理由不是洁癖：float 的舍入方向和精度损失无法与 Solidity 语义对齐，
而这个系统要求回测结果字节级可复现。

### 2.5 只追加 + 不插值

原始数据和审计事件只追加，不覆盖不删除，不用插值补空缺。
错误必须保留 chain / PoolKey / block 范围 / endpoint / 尝试次数 / 原因，
但脱敏密钥。

## 三、值得带走的：五个会复发的坑

这五条是 V1 真实踩过的，不是假想。

### 3.1 分区写入会静默丢行

2026-09-18 的参考运行 `run-680e65f4a59842d98b1712a45280779d`：
`event_index` 记录 3,739 行 / 3,266 个事件块，而 Parquet 分区里只有
3,737 行 / 3,264 个——**丢了两行，没有任何报错**。

原因不是链上事件，是当一个采集区间写入另一个区间已经建过的分区单元格时。

**教训**：写入必须对账。任何"我以为写进去了"都不成立，只有计数能证明。

### 3.2 门禁红着但没人管，等于没有门禁

2026-09-23 的 `CI_GATE_DEBT` 文档记录：一个候选同时引入了格式化违规和
一个真实运行时缺陷（取消非终态运行抛 `TypeError`），却被 APPROVED。

根因不是评审不尽责，是**范围**：评审跑的是自己文件范围内的 ruff/mypy，
而仓库级 mypy 从 09-17 起就有 149 个错误红着，挡不住任何提交。

那个 TypeError 被中止点遮住了约两天——mypy 在第一个重复模块名处就停止，
它的输出里从来没出现过第 2 条错误。

**教训**：全量门禁要么跑，要么就承认它不存在。文件范围内通过 ≠ 仓库通过。

### 3.3 两条规则可以联立无解

2026-09-20 的 bootstrap 提案记录了一次真实死锁：

- 规则 A：任务带 `superseded_by` 时，ARCHITECTURE.md §2.2 那一行**必须**写出后继
- 规则 B：SUPERSEDE 层的封存**只允许**改 `todo/config.yaml`

A 要求改文档，B 禁止改文档。靠自身 retry 修不了，需要 Owner 手术，
而且需要两次（第二次是因为删运行时记录导致编号回退，撞上旧分支名）。

**教训**：立硬规则前必须问"哪一层执行它，那一层够得着吗"。
没有这样的层，就该做成检查而不是规则。
（v2 的 `tools/prophet/` 采纳了这条：每条检查都有真实的执行者。）

### 3.4 Provider 限制不写下来就会被重新踩

Alchemy Free 每次只能取 10 个块的日志——这个限制**不在错误里**，
它返回成功，只是数据少。不测一次就写进 ADR，入库跑到一半才会炸。

**教训**：外部服务的限制要主动测出来并记录，包括"成功但不完整"的那种。

### 3.5 评审能看出方案错了，但改不了

T109 的一次 FAIL 评审写出了大量设计级发现（候选没有扩展 `AuditEvent`
携带它需要的 cursor；没有端到端跑通新接口），判断完全正确。
但 verdict 只能填 FAIL，而改设计的唯一路径要走
planner → plan-reviewer → 独立评审 → 封存。

**发现被记录了，方案却动不了。** 这是 v2 把 critic 改成"提建议 + 提下一轮
假设"而不是"给 verdict"的直接原因。

## 五、V2 从哪里开始

V1 停在 P06（回测进行中），P07 风险只有 1/4，P08 Web 控制台和
P09 签名实盘**一行代码都没写**。

也就是说 V1 把地基（协议/存储/重建/特征/回测）做得很扎实，
但**产品的一半没开始**，而且已经证明这套地基的维护成本很高。

V2 的第一个假设因此不是"继续做回测"，而是：

> **地址未验证 + provider 能力限制未测 → 先花 10 分钟确认地基是真的。**

具体见 `.prophet/spec.md`。
